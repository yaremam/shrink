# 006 — Coding standards (Dart)

## User story

As the Shrink! project owner,
I want a documented coding standard for the Flutter client,
So that the client gets the same closable gap between "tooling
catches the mechanical stuff" and "a human has to eyeball everything
else" that 004 gave the backend.

## Acceptance criteria

- **AC-1**: `CODING_STANDARDS.md` gains a "Dart" section covering
  conventions the linter can't check: widget structure (Stateless vs.
  Stateful), doc comments on public API, naming, and testing
  conventions (`flutter_test`, per 005).
- **AC-2**: `client/analysis_options.yaml` (already generated by
  `flutter create`, using `package:flutter_lints/flutter.yaml`) is
  confirmed as the enforced half — no new lint config is written,
  since one already exists and `flutter analyze` already runs clean
  against it.
- **AC-3**: `flutter analyze` continues to exit clean after this
  feature (nothing to retroactively fix was found — 005 already
  landed analyze-clean).
- **AC-4**: `docs/architecture.md` references the updated standards
  doc if not already covered by 004's reference.
